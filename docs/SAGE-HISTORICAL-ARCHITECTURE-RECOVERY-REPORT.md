## 2. The SAGE Lineage Model

To govern the evolution of concepts from initial inspiration to immutable production records, SAGE implements the following sequential lineage flow:

$$\text{Origin Idea} \longrightarrow \text{Research Exploration} \longrightarrow \text{Architecture Hypothesis} \longrightarrow \text{Validation} \longrightarrow \text{Capability Proposal} \longrightarrow \text{Implementation} \longrightarrow \text{Archive Record}$$

### Lineage State Definitions:
1. **Origin Idea:** Initial conceptual spark, analogy, or inspiration (often derived from advanced systems research, cognitive frameworks, or analogical systems).
2. **Research Exploration:** Active analysis of feasibility, theoretical constraints, and mapping of conceptual requirements.
3. **Architecture Hypothesis:** Formal modeling of interfaces, system boundaries, and structural specifications (e.g., drafting dry-run rehydration contracts).
4. **Validation:** Active verification of the hypothesis via sandboxed simulation, analytical analysis, or shadow telemetry observation.
5. **Capability Proposal:** Structuring of concrete development files, rollback parameters, and dependency maps under strict governance criteria.
6. **Implementation:** Coding of the validated capability within a safe, isolated experimental namespace.
7. **Archive Record:** Final verification and lock-in, archiving the completed work as a validated baseline.

## 6. Discarded Concepts & Retired Approaches

To preserve engineering history and prevent future developers from retreading failed architectural paths, SAGE documents historical design decisions that were intentionally retired or discarded.

### 6.1. Discarded: Centralized Stateful Database Architecture
* **Description:** An early proposal to track all agent events and decision traces inside a centralized, stateful database (e.g., PostgreSQL or Redis) running alongside SAGE.
* **Why Discarded:**
  1. **Single Point of Failure:** Introduced a critical, heavy operational dependency that degraded SAGE's lightweight runtime.
  2. **Audit Tampering Risk:** A compromised state database allowed attackers to rewrite agent logs and cover up privilege escalation attempts.
  3. **Replacement:** Replaced by the **Stateless Context Rehydration (SAGE-SCR)** model and **CMAPS v1.0**, which rely on decentralized, client-held, cryptographically signed payload chains.

### 6.2. Discarded: Synchronous Thread-Blocking Execution Guardrails
* **Description:** An early safety model that intercepted every model API request and blocked the active execution thread until an asynchronous security server returned an approval token.
* **Why Discarded:**
  1. **Latency and Timeouts:** Caused severe performance bottlenecks and API timeout cascading failures.
  2. **Replacement:** Replaced by the **Active Client Hook (SAGE-ACH)** passive observation paradigm, coupled with **Graceful Intercept and Recovery Loops (SAGE-SDR)**, which intercept errors at natural boundaries without blocking execution pipelines.

### 6.3. Retired: Raw Unencrypted Diagnostic API Bundles
* **Description:** Packaging runtime diagnostics, environmental variables, and call stacks into raw JSON bundles sent over standard HTTP endpoints for debugging.
* **Why Retired:**
  1. **Security Vulnerability:** Environmental dumps contained sensitive API keys, session tokens, and system secrets.
  2. **Replacement:** Replaced by the **SPEK Policy Vault** and secure cryptographic hashes (SHA-256) inside **Cross-Model Audit Payloads**, ensuring only sanitized, non-sensitive telemetry is emitted.

## 7. Missing Continuity Gaps Discovered

During this historical knowledge synchronization pass, the following continuity gaps between proposed concepts and active implementations were identified:

1. **Cross-Session Rehydration Validation Drift:**
   * *The Gap:* While CMAPS v1.0 specifies the structure of `recovery_checkpoints` and `rehydration_token`, the stateless rehydrator lacks an automated, end-to-end integration test validating context recovery across completely different, decoupled session instances.
   * *Mitigation:* Map out a formal cross-session trace validation test within the future **SAGE Cryptographic Session Receipt Chain (SAGE-CRC)** implementation.
2. **Decentralized Signature Key Rotation:**
   * *The Gap:* CMAPS attestation signatures rely on static validator public keys (`sage_validator_pubkey_01`). There is no specified protocol for rotating or revoking these keys in a multi-agent environment.
   * *Mitigation:* Document a key rotation proposal in the next strategic research track.
3. **Rollback Timeout State Recovery:**
   * *The Gap:* The Graceful Intercept manager successfully catches boundary violations but does not handle cases where the recovery checkpoint itself fails to rehydrate due to an external model timeout.
   * *Mitigation:* Introduce a lightweight, local state rollback fallback mechanism within the isolated runner.
