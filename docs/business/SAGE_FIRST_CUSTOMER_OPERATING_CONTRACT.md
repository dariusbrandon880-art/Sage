# SAGE First-Customer Operating Contract

## Purpose

SAGE is operated against itself as its first demanding customer. The product is not accepted because its architecture is impressive or its deterministic test suite is green. It is accepted when a real customer workflow is completed, observed, evidenced, independently verified, economically measured, and converted into reusable capability.

## Customer

- Customer: `SAGE_FIRST_CUSTOMER`
- Customer role: first demanding customer / product proving ground
- Primary operator identity: `[SAGE::C2::CHATGPT]`
- Engineering authority: `[SAGE::ENGINEER::JULES]`
- Intelligence authority: `[SAGE::INTEL::GEMINI]`
- Human authorization authority: Mission Director

## Canonical Product Loop

`PROBLEM -> BASELINE -> MISSION CHARTER -> 5-FLIGHT EXECUTION -> OBSERVED EFFECTS -> FAILURE/RECOVERY -> EVIDENCE -> INDEPENDENT EVALUATION -> ECONOMIC MEASUREMENT -> QUALIFICATION -> REUSABLE CAPABILITY -> NEXT HARDER MISSION`

## Customer Acceptance Gates

### Gate A — Engineering

Must prove:

- canonical repository state is rehydrated;
- mission hierarchy is aligned;
- authorized work executes;
- deterministic verification passes;
- evidence is SHA-bound where required;
- identity/provenance is preserved.

### Gate B — Empirical

Must prove through attributable observation:

- the customer can observe the intended identity/state surface;
- the required interfaces converge on the same mission state;
- execution effects match the declared mission;
- failures and recovery are visible and recorded;
- evidence supports the acceptance claim.

**Engineering PASS without empirical PASS is `ENGINEERING_VERIFIED`, never `ACCEPTED`.**

## Business Measurement

Measure the completed workflow, not model-token cost alone:

- completion status;
- elapsed execution time;
- human interventions;
- direct execution cost;
- customer/workflow value;
- failures;
- recoveries;
- evidence count/references;
- reusable capability produced;
- whether the next comparable mission becomes easier, faster, cheaper, or more reliable.

The primary economic question is: **what did it cost to finish the job, what value did finishing the job create, and what reusable capability reduced the cost of the next job?**

This follows current enterprise-agent economics research from McKinsey emphasizing fully loaded completed-workflow cost and reuse rather than token price alone.

## Identity, Authorization, and Auditability

Every agent action must have attributable identity and an authorization boundary. SAGE must preserve enough evidence to connect action, intent, authority, result, and human authorization. This aligns with current NIST work on agent identity, authorization, auditing, non-repudiation, and human-agent delegation.

## Evaluation

Evaluation is part of the workflow rather than an afterthought. SAGE should use reproducible probes and structured audit trails that connect claims/results to supporting evidence, while treating post-deployment observation as distinct from pre-deployment testing.

## Anti-Gaming Rule

A score, green test, or automated receipt cannot establish capability by itself. SAGE must preserve independent evidence and must detect cases where an agent optimizes for the evaluation rather than the intended customer outcome.

## Qualification Standard

A capability is promoted only when:

**Build + Verification + Evidence + Reusable capability + Customer-observed outcome**

exist at the declared acceptance boundary.

## Product Boundary

The repository governs the SAGE runtime, customer workbench, evidence model, and acceptance protocol. The repository cannot alter the native ChatGPT application renderer. Therefore a repository-defined nameplate is a governed attribution stream; native UI rendering remains an empirical customer acceptance question.
