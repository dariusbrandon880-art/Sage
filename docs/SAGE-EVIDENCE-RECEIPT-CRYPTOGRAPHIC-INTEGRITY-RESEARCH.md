# SAGE Evidence Receipt Cryptographic Integrity Research Specification

This document presents the **Security Architecture Research Specification** for the cryptographic integrity protection of SAGE evidence receipts. It evaluates how SAGE can implement tamper-evident, non-repudiable provenance validation for its operational logs and validation traces.

This is a research specification and does **not** introduce any production cryptography keys, active runtime enforcement, or automated promotion systems. Core protected directories (`sage/runtime/`, `sage/core/`, `sage/acr/`) remain entirely untouched.

---

## 1. Purpose

The objective of this research track is to define a cryptographic framework enabling SAGE to:
- Verify that active evidence packages and capability passports have not been altered after creation (**Tamper-Evidence**).
- Establish absolute proof of validator and reviewer signatures, preventing impersonation (**Non-Repudiation**).
- Chronologically bind validation events in a cryptographically linked ledger, establishing a verifiable sequence of state transitions (**Lineage Chaining**).

---

## 2. Evidence Integrity Model

We model SAGE's evidence integrity around three pillars of security architecture:

1. **Deterministic Serialization (Canonicalization):**
   To generate consistent cryptographic signatures, receipt payloads must be normalized before hashing (e.g. key sorting, stripping whitespaces, enforcing standard float precision).
2. **Asymmetric Cryptographic Signatures:**
   Every receipt must contain an active digital signature generated by the validator or reviewer's private key (e.g. Ed25519) and verified using their public key registered in the Agent Passport ledger.
3. **Ancestral Hash Binding (Chaining):**
   Every new receipt payload must contain the secure hash of the preceding receipt, programmatically constructing a tamper-evident chain of validation events.

---

## 3. Receipt Canonical Structure

To guarantee deterministic hashing, SAGE evidence receipts are canonicalized into the following structured format:

```json
{
  "canonical_header": {
    "receipt_id": "rcpt_7f3b89012cd4e5f6",
    "parent_receipt_hash": "7f83b123d456e7f8... (or null for root)",
    "timestamp": "2026-03-31T12:00:00.000000Z"
  },
  "canonical_body": {
    "capability_id": "cap_sdr_sim_engine",
    "validator_id": "val_system_v1",
    "validation_hash": "a4f89d34e2c83f94... (sha256 of execution output)",
    "evidence_reference": "docs/SAGE-SDR-READINESS-SPECIFICATION.md"
  },
  "canonical_attestation": {
    "public_key": "ed25519_pub_...",
    "signature": "sig_..."
  }
}
```

---

## 4. Identity and Signing Separation

To preserve SAGE's human-in-the-loop authority, we establish a strict separation between machine/agent identities and human review authorizations:

- **Machine/Agent Signing (Automation):**
  Agent nodes (such as Jules) and validation modules (such as `val_system_v1`) sign evidence receipts and validation outputs automatically to prove execution integrity.
- **Human Signing (Governance):**
  Machine signatures **never** carry capability promotion authority. Final promotion from `PROPOSED` to `VALIDATED` requires a manual human signoff trace generated by an authorized supervisor's private key, sealing the receipt inside the designated Main Archive directory.

---

## 5. Lineage Verification Concept

The verification algorithm recursively validates the entire lineage chain starting from any target receipt back to SAGE's constitutional root receipt:

```
[ Root Receipt ] <─── [ Receipt 001 ] <─── [ Receipt 002 ] <─── [ Target Receipt ]
      ▲                     ▲                     ▲                     ▲
  Signature             Signature             Signature             Signature
    Valid                 Valid                 Valid                 Valid
```

### 5.1 Verification Algorithm Steps:
1. **Canonicalize:** Parse and sort the target receipt fields.
2. **Verify Signature:** Check `canonical_attestation.signature` against `canonical_attestation.public_key` over the header and body fields.
3. **Trace Parent:** Fetch the preceding receipt matching `parent_receipt_hash`.
4. **Recurse:** Repeat steps 1–3. Any signature failure, missing parent, or hash mismatch instantly invalidates the entire traceability lineage, blocking capability promotion.

---

## 6. Governance Alignment

The cryptographic integrity model maps directly to SAGE’s standard lifecycle gates:

$$\text{Research} \rightarrow \text{Validation} \rightarrow \text{Evidence} \rightarrow \text{Human Review} \rightarrow \text{Master Archive}$$

- **Evidence Gate:** Programmatically binds machine-signed receipts.
- **Human Review Gate:** Human supervisor verifies machine signatures, performs final manual review, and adds their authorizing human signature.
- **Master Archive:** Stores the double-signed (machine + human) receipts in the designated Main Archive destinations.

---

## 7. Security Risks

- **Key Compromise:** Theft or exposure of an authorized supervisor's private signing key.
  * *Mitigation:* Require multi-signature (M-of-N) approvals for high-risk canonical promotions.
- **Replay Attacks:** Re-submitting an old, approved receipt to authorize a new, un-reviewed capability branch.
  * *Mitigation:* Enforce sequential, non-repeating nonce ledgers inside `nonce_ledger.py`.
- **Pre-Image Attacks:** Manipulating simulated logs to generate a matching validation hash.
  * *Mitigation:* Utilize high-strength SHA-256 or SHA-512 hashing algorithms for all execution trace outputs.

## 8. Future Engineering Requirements

To transition this research into active experimental prototypes:
1. **Asymmetric Crypto Library:** Install `pynacl` (for Ed25519) under experimental dependencies.
2. **Key Store Ledger:** Implement a secure, local, file-based key store (e.g. `keystore.json` under `.sage/`) to store registered public keys.
3. **Trace Validation CLI:** Create a developer CLI tool inside `sage/experimental/act/` to recursively audit and verify the lineage chain of archived JSON receipts.
