SAGE continues to use the same governed build technique used throughout the career work:

```text

    ↓

    ↓

    ↓

    ↓

    ↓

```

A research pass is not mandatory for every task. It is used when repository evidence identifies an unresolved question, blocked build, unfamiliar failure mode, or other gap where external evidence can materially improve the solution.

This is a workflow finding, not a new architecture.

## 3. Blockers as Early Boss Signals

A newly observed design finding is that a **blocked build or meaningful blocker can be an early signal for Boss-candidate detection**.

The intended interpretation is:

```text
BLOCKER / DIFFICULT OBSTACLE
          ↓
    INVESTIGATE / RECON
          ↓
 SUPER SEARCH IF NEEDED
          ↓
      BOUNDED BUILD
          ↓
  VERIFIED BREAKTHROUGH
          ↓
 POSSIBLE BOSS CANDIDATE
```

The blocker itself is **not automatically a Boss**.

The existing Boss contract remains authoritative: not every hard task is a Boss. Boss classification is reserved for a meaningful challenge/milestone whose verified outcome represents demonstrated capability and a recognizable progression closure point. The Mission Director retains final authority over classification.

Therefore:

```text
BLOCKER = detection signal / candidate trigger
BOSS    = governed classification after evaluation
```

## 4. What Makes the Signal Stronger

A blocker becomes a stronger Boss candidate when the work requires meaningful demonstrated capability and has a consequential verified outcome, such as:

- a persistent or high-impact obstacle is eliminated;
- a difficult failure mode is removed;
- a substantial capability is established;
- a qualification is achieved;
- a reusable capability or asset is secured;
- multiple capabilities, dependencies, sorties, evidence artifacts, or coordinated work are required;
- the verified result materially advances a frontier or closes a meaningful progression milestone.

These are candidate indicators, not a finalized scoring formula.

## 5. Boss Classes Remain Locked

Only two Boss classes exist:

```text
⭐   BIG BOSS
⭐⭐  MAJOR BOSS
```

No additional Boss tier is introduced by this finding.

Big/Major remain difficulty classes rather than fixed XP payouts.

## 6. Boss Outcomes Remain Locked

### Elite Kill ⚔️

A verified Boss outcome that eliminates a meaningful obstacle, threat, blocker, defect, or failure mode.

### Elite Capture ┃

A verified Boss outcome that secures or establishes a meaningful capability, qualification, intelligence finding, or reusable asset.

A single Boss can produce both outcomes when the evidence supports both.

## 7. Career Accounting Remains Separate

Bosses do not replace Points, XP, qualification, badges, or promotion.

```text
BOSS
 ↓
VERIFIED OUTCOME
 ↓
QUALIFIED PERFORMANCE
 ↓
POINTS
 ↓
XP
 ↓
CAREER / RANK CONSEQUENCE
```

The Points→XP economy already established in the preceding career work remains the accounting path. Boss classification must not become an alternate currency or automatic promotion shortcut.

## 8. Evidence and Persistence

Boss recognition must remain downstream of real canonical state and evidence.

No invented Boss health, damage, kill state, or progress values are permitted merely for immersion.

Boss attempts and failures remain historical evidence; retrying a challenge does not erase prior attempts.

Repeated work does not create automatic career inflation unless it produces additional verified value.

## 9. Five-Flight Boundary

This finding does not alter the Five-Flight operating model.

```text
F1–F5 = reusable execution vehicles
BOSS   = challenge object
```

A Boss may require one or multiple flights, and flights may participate in multiple Boss encounters. No permanent mapping is created.

## 10. Queue #05 Implementation Question

The next build question is now narrowed to:

> **How should SAGE represent and evaluate a real Boss candidate using existing canonical mission/sortie, event, evidence, qualification, progression, and roster seams without creating a parallel game engine or promoting every blocker into a Boss?**

The first implementation should remain the smallest governed primitive that can represent this real-world challenge relationship.
